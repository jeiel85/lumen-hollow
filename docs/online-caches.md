## 1. 전제: 현재 코드에서 확인한 사실

설계는 아래 사실에 기대고 있다. 마을 생성 방식이 바뀌면 이 문서도 다시 봐야 한다.

1. **마을 배치는 모두에게 같다.** `World` 생성자는 고정 시드 `new Rng(20261105)`로 도로·블록·가로등·충돌체·수색 지점을 만든다(`src/world.js:92`). 그래서 같은 버전을 받은 플레이어는 같은 좌표계를 공유한다.
2. **수색 지점의 내용물은 판마다 다르다.** `startGame()`이 `world.reset(무작위 시드)`로 아이템을 다시 섞는다(`src/main.js:177`, `src/world.js:893`). 따라서 "여기에 퓨즈가 있었어요" 같은 위치 정보는 다른 판에서 거짓이 된다. 미리 정한 문구에서도 이런 말은 뺀다(11절).
3. **플레이는 판 단위이고 저장이 없다.** 판을 시작할 때마다 체력·배터리·인벤토리·트럭 연료가 초기화되고, `localStorage`에는 최고 기록(`lumen.best`)만 남는다. 게임 속 1시간이 7.5초라서 하루는 180초(낮 약 94초, 밤 약 86초)다(`src/env.js:4`). "하루 한 번" 같은 규칙에 게임 속 하루를 쓰면 판을 다시 시작해 쉽게 우회할 수 있다. 그래서 재사용 규칙은 **실제 시간**을 기준으로 한다.
4. **아이템 수치** (`src/main.js`, `src/world.js:903`, `src/player.js`, `src/vehicle.js`):

   | 아이템 | 효과 | 한 판에 마을 전체 수량 | 보관 방식 |
   |---|---|---|---|
   | 퓨즈 | 꺼진 배전함 하나를 켠다. 8곳을 켜면 승리 | 11개 + 시작 1개 | 개수 |
   | 배터리 | 손전등 +45%(켜 두면 1.15%/초 소모, 약 39초) | 13개 | **바로 적용되고 쌓이지 않음** |
   | 붕대 | 체력 +35, 최대 5개 보관 | 8개 | 개수 |
   | 연료통 | 트럭 연료 +40(탈 때 부음) | 7개 | 개수 |

   수색 지점은 68곳(아이템 39 + 빈 곳 29)이다. 2026-11-06에 `World`를 Node에서 직접 생성해 센 값이다.
5. **빛이 곧 안전이다.** 켜진 가로등의 반경 5.6m(`LAMP_RADIUS`) 안으로는 그늘이가 들어오지 못하고, 그 안에서는 손전등이 충전되고 체력이 회복된다. 그늘이는 빛이 닿지 않는 곳에서만 생긴다(`src/shades.js`의 `_spawn`). 가로등은 52개다.
6. **전투 시스템은 없다.** 그늘이는 손전등·전조등으로 오래 비추거나 트럭으로 들이받아 흩어 버린다. 체력 감소는 그늘이에게 닿을 때만 생긴다.
7. **빌드 없는 정적 사이트다.** GitHub Pages에 배포하고, 서버와 분석 도구가 없다. **지금은 하루에 몇 명이 플레이하는지도 모른다.** 이 기능의 서버 기록이 첫 이용 데이터가 된다.
8. **클라이언트 코드는 공개다.** API 주소와 요청 형식은 누구나 볼 수 있다. 브라우저 밖에서 API를 직접 부르는 사람을 전제로 설계한다.
9. **배포 직후에는 옛 JS와 새 HTML이 섞일 수 있다**(PR #4에서 겪음). API는 버전 경로(`/v1`)로 고정하고, 클라이언트는 모르는 필드와 모르는 종류를 무시한다.

## 2. 경험 목표와 비목표

목표
- 정전된 마을에서 **나보다 먼저 버틴 누군가의 흔적**을 발견하는 순간을 만든다. 빛과 생존이라는 테마를 해치지 않는다.
- 남긴 사람은 나중에 "내 보급품을 누가 썼다"는 소식을 받는다. 이 피드백이 비동기 온라인의 핵심 보상이다.

비목표 (이번 범위 밖)
- 실시간 멀티플레이, 채팅, 친구, 랭킹, 계정·로그인
- 서버가 판정하는 게임 밸런스 (혼자 하는 판의 치트 방지)
- 자유 텍스트와 닉네임

### 3.1 후보 비교

| 후보 | 둔 사람이 내는 것 | 받는 사람이 얻는 것 | 테마 적합 | 구현 부담 | 제안 |

| 보급 상자 — 연료통 | 연료통 1개 | 연료통 1개 | 좋음(트럭과 연결) | 작음 | **1단계** |

### 3.2 퓨즈를 빼는 이유

퓨즈는 진행의 핵심 자원이다. 마을의 11개와 시작할 때 가진 1개, 모두 12개 중 8개가 필요하다. 상자 하나가 퓨즈를 8명에게 나눠 주면 탐색 없이 구역을 켤 수 있어 목표 자체가 비게 된다. 넣는다면 "1명만, 1번만 받는 퓨즈"처럼 재사용을 빼야 하는데, 이는 '넉넉하게'라는 출발점과 맞지 않는다.

### 3.3 총 대신 조명탄 권총

| 기준 | 총 | 조명탄 권총 |
|---|---|---|
| 필요한 새 시스템 | 조준 판정, 피해·체력(그늘이), 탄약, 맞힘 표시, 사망 연출 | 발사 궤적, 일정 시간 켜지는 광원, 새 아이템 |
| 기존 규칙 재사용 | 거의 없음 | `lightAt`·광원 풀·그늘이 밀어내기를 그대로 씀 |
| 테마 | "어둠을 쏴서 이긴다"로 바뀜 | "빛을 던져 버틴다"를 유지 |
| 남용·밸런스 | 공유 총이 여러 사람에게 가면 밤의 긴장이 사라짐 | 1발 1회용이라 수치로 조절하기 쉬움 |

제안: 총은 넣지 않는다. 조명탄 권총은 보급 상자의 성과를 본 뒤 3단계에서 검토한다.

## 4. 게임 안 흐름

1. **불러오기**: 판을 시작할 때 활성 보급품 목록을 한 번 받는다(최대 3초 기다림, 13절). 판 도중에는 다시 받지 않는다.
2. **보이기**: 남의 보급품은 인도 위 작은 상자로 놓이고, 수색 지점(따뜻한 노란 반짝임)과 구별되게 청록색으로 반짝인다. 가까이 가면 "다른 생존자가 남긴 붕대 · 6번 남음 · '같이 버텨요'"처럼 보인다.
3. **쓰기**: 기존 뒤지기와 같은 "E(상호작용 버튼) 길게 1초"로 쓴다. 서버가 확인한 뒤에 아이템을 준다. 같은 상자를 다시 보면 프롬프트가 **"고마워요 보내기"**로 바뀐다.
4. **두기**: 새 키(G, 터치에서는 '두기' 버튼)를 누르면 가장 가까운 빈 슬롯(3m 안)에 반투명 상자가 보이고, 둘 것(가진 것만)과 문구를 고르는 작은 메뉴가 뜬다. 요청하는 동안에는 물건을 맡겨 두었다가(그새 써 버리지 않게) 서버가 거절하면 돌려준다. E에 두기를 겹치지 않는 이유는 인도 어디서나 프롬프트가 떠서 뒤지기·트럭 타기와 충돌하기 때문이다.
5. **소식**: 타이틀 화면에 "당신이 남긴 보급품 3개를 다른 생존자 7명이 썼고, 4명이 고마워했어요" 한 줄을 보여 준다.
6. **끄기**: 일시정지·타이틀 화면에 "온라인 보급품" 켜기/끄기를 둔다. 끄면 아무 요청도 보내지 않는다.

## 5. 재사용 규칙

### 5.1 원칙: 서버는 남에게 영향을 주는 상태만 지킨다

- 이 게임은 혼자 하는 게임이라, 클라이언트를 고쳐 붕대를 무한히 받아도 **그 사람의 판만 쉬워진다.** 이런 밸런스 규칙은 클라이언트에서 지킨다.
- 남의 경험을 바꾸는 상태(남은 사용 횟수, 수명, 슬롯 차지, 고마워요 수)는 **서버가 강제**한다.

### 5.2 제안 수치

| 규칙 | 제안값 | 강제 위치 | 이유 |
|---|---|---|---|
| 상자당 총 사용 횟수 N | **8회** | 서버 | 1개를 내놓아 8명을 돕는다. '넉넉함'과 '언젠가 바닥남'의 균형 |
| 같은 플레이어의 같은 상자 재사용 | **24시간에 1회** | 서버 | 판을 다시 시작해 같은 상자를 계속 쓰는 것을 막음 |
| 둔 사람 본인의 사용 | **불가** | 서버 | 판 끝에 두고 다음 판에 꺼내 쓰는 '판 사이 저장소'가 되는 것을 막음 |
| 상자 수명 | **72시간** | 서버 | 플레이어가 적은 초기에도 누군가 볼 시간 확보 |
| 고마워요 1건당 연장 | **+12시간**, 생성 후 **최대 7일** | 서버 | 고마움이 보급품을 오래 살린다. 상한이 있어 조작해도 영원하지 않음 |
| 고마워요 자격 | **그 상자를 실제로 쓴 사람만, 1회** | 서버 | 자기 상자에 고마워요를 몰아주는 조작을 막음 |
| 한 판에 남의 보급품 사용 | **3회까지** | 클라이언트 | 마을 전체 아이템 39개 대비 약 8% 증가로 묶음 |
| 플레이어당 동시에 살아 있는 보급품 | **3개** | 서버 | 한 사람이 마을을 채우지 못하게 함 |
| 마을 전체 활성 보급품 | **400개** (슬롯 516칸) | 서버 | 최악의 경우에도 빈 슬롯이 남게 함 |

### 5.3 얼마나 쉬워지나

- 한 판에 남의 보급품을 최대 3번 쓰면 붕대 3개(+105 체력) 또는 배터리 +90% 정도를 더 얻는다. 마을에 원래 있는 붕대 8개·배터리 13개에 비하면 작다.
- 퓨즈가 빠져 있어 **목표(구역 8곳 켜기)에 걸리는 탐색량은 그대로**다. 보급품은 버티기를 돕지만 진행을 대신하지 않는다.
- 랜턴(2단계)은 반경을 가로등보다 작은 4m로 하고, **충전·회복을 주지 않는다.** 숨을 곳은 되지만 머무르며 자원을 채우는 곳은 되지 않는다. 한 판에 보이는 랜턴은 고마워요가 많은 순서로 4개까지로 제한한다. 랜턴은 둔 사람 본인에게도 보인다(구조물은 공유 공간의 일부라는 데스 스트랜딩식 해석). 보급 상자와 달리 판 사이로 옮길 자원이 없어서 본인 이득이 작다.

### 5.4 '총 사용 횟수'를 두는 것의 대가

N을 두면 봇이 새 ID를 계속 만들어 남의 상자를 비울 수 있다(10절의 '고갈'). 이 위험을 없애려면 N 없이 수명만 두는 방법도 있다. 비교:

| 방식 | 장점 | 단점 |
|---|---|---|
| N회 + 수명(제안) | "누군가 다 써 버렸다"는 흔적이 의미를 만든다. 남긴 사람에게 "8명 모두 썼어요"라는 완결 소식 | 고갈 공격 가능(피해는 아이템 몇 개, 레이트 리밋으로 완화) |
| 수명만, 무제한 | 고갈 공격 불가. 규칙이 단순 | 한 상자가 마을의 고정 자판기가 됨. '넉넉함'의 무게가 사라짐 |

## 6. 위치: 자유 좌표 대신 슬롯

### 6.1 슬롯 정의

- 각 블록(5×5)의 인도 중심선(블록 중심에서 11m) 네 변에 3m 간격으로 6칸씩 둔다. 블록당 24칸, 전체 **600칸**이다.
- 번호: `slot = ((row * 5 + col) * 4 + side) * 6 + i` (side: 0=남, 1=북, 2=동, 3=서 / i: 0~5, 변 위 위치 −7.5, −4.5, −1.5, 1.5, 4.5, 7.5m).
- 그중 충돌체(가로등 기둥·가로수·건물 등)에서 1m, 배전함·수색 지점에서 2m 안에 드는 칸을 빼면 **516칸**이 빈다(2026-11-06 Node에서 생성한 마을로 계산). 빈 칸 중 93칸은 가로등 빛 반경 안이다.
- 슬롯 표는 클라이언트가 마을을 만든 뒤 계산한다. 서버는 `0 ≤ slot < 600`인지와 막힌 84칸 목록에 없는지만 확인한다. 막힌 칸 목록은 슬롯 계산 스크립트의 출력을 서버 코드에 상수로 넣는다.

### 6.2 마을 배치 버전(`layout`)

- 슬롯이 비는지는 시드로 생성한 가로수 위치에 달려 있다. `world.js`의 생성 순서나 상수를 바꾸면 슬롯 표도 바뀐다.
- 그래서 모든 보급품에 `layout`(현재 1)을 붙인다. 마을 생성이 바뀌면 `layout`을 올리고, 서버는 현재 `layout`의 보급품만 돌려준다. 옛 보급품은 자연 만료된다.

### 6.3 자유 좌표와 비교

| 기준 | 슬롯(제안) | 자유 좌표(x, z) |
|---|---|---|
| 서버 검증 | 정수 범위 + 금지 목록 | 경계·충돌체 판정을 서버에 옮겨야 함(three.js 의존 마을 생성을 서버에서 돌려야 함) |
| 겹침 방지 | 한 슬롯에 하나(고유 제약) | 거리 검사 쿼리 필요 |
| 표현 자유 | 인도 위로 한정 | 어디든 |
| 마을 변경 대응 | `layout` 버전으로 정리 | 같음 |

## 7. 데이터 모델

실제로 쓰는 스키마는 [server/schema.sql](../server/schema.sql)이다. 아래는 설계 당시의 핵심 테이블이고, 구현에서 더한 것은 17절에 있다.

D1(SQLite) 기준이다. 시각은 Unix 밀리초 정수다(현재 약 1.8조라 32비트에 들어가지 않는다). SQLite의 `INTEGER`는 64비트라 그대로 담긴다. Postgres로 옮길 때는 `INTEGER`가 32비트이므로 **시각 열(`*_at`)을 `BIGINT`로 바꿔야 한다.** 나머지 타입과 부분 인덱스는 그대로 옮길 수 있다.

자식 테이블(`uses`, `thanks`)의 외래 키에는 일부러 연쇄 삭제를 걸지 않는다. 부모를 먼저 지우는 실수가 보존 기간을 조용히 줄이지 않고 오류로 드러나게 하기 위해서다. 삭제 순서는 12절에 있다.

```sql
-- 활성·만료 보급품
CREATE TABLE caches (
  id          TEXT PRIMARY KEY,            -- 서버가 만든 무작위 ID (예: c_ + 16바이트 base32)
  layout      INTEGER NOT NULL,            -- 마을 배치 버전 (현재 1)
  slot        INTEGER NOT NULL CHECK (slot >= 0 AND slot < 600),
  kind        TEXT    NOT NULL CHECK (kind IN ('bandage', 'fuel', 'battery', 'lantern')),
  note        INTEGER NOT NULL DEFAULT 0,  -- 미리 정한 문구 번호 (11절)
  owner       TEXT    NOT NULL,            -- sha256(플레이어 ID). 응답에는 절대 넣지 않음
  charges     INTEGER,                     -- 남은 사용 횟수. lantern은 NULL
  thanks      INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL,
  expires_at  INTEGER NOT NULL,
  removed_at  INTEGER,                     -- 만료 정리·본인 삭제·관리자 삭제 시각
  removed_by  TEXT CHECK (removed_by IN ('expired', 'owner', 'admin'))
);
-- 한 슬롯에는 정리되지 않은 보급품이 하나만 있을 수 있다.
CREATE UNIQUE INDEX caches_slot_live ON caches (layout, slot) WHERE removed_at IS NULL;
CREATE INDEX caches_owner ON caches (owner) WHERE removed_at IS NULL;

-- 사용 기록 (24시간 1회 판정, 고마워요 자격, 지표)
CREATE TABLE uses (
  cache_id  TEXT    NOT NULL REFERENCES caches (id),
  user_hash TEXT    NOT NULL,              -- sha256(플레이어 ID)
  used_at   INTEGER NOT NULL
);
CREATE INDEX uses_lookup ON uses (cache_id, user_hash, used_at);

-- 고마워요 (상자당 1인 1회)
CREATE TABLE thanks (
  cache_id  TEXT    NOT NULL REFERENCES caches (id),
  user_hash TEXT    NOT NULL,
  at        INTEGER NOT NULL,
  PRIMARY KEY (cache_id, user_hash)
);

-- 접속 플레이어 수(지표의 분모). 하루에 한 번만 기록
CREATE TABLE seen (
  day       TEXT NOT NULL,                 -- UTC 날짜 'YYYY-MM-DD'
  user_hash TEXT NOT NULL,
  PRIMARY KEY (day, user_hash)
);

-- 서버 설정 (킬 스위치 등)
CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

핵심 쓰기는 한 트랜잭션(D1 batch / Postgres 함수)에서 처리한다.

- **두기**: 같은 슬롯의 만료된 행을 `removed_by='expired'`로 정리 → 소유자 활성 수·전체 활성 수 확인 → 삽입. 고유 인덱스가 동시 요청을 막는다.
- **쓰기**: `UPDATE caches SET charges = charges - 1 WHERE id = ? AND charges > 0 AND removed_at IS NULL AND expires_at > :now AND owner <> :user AND NOT EXISTS (24시간 안의 같은 사람 사용)` → 바뀐 행이 1개일 때만 `uses`에 기록한다.
- **고마워요**: `uses`에 기록이 있을 때만 `thanks`에 넣고, `expires_at = MIN(expires_at + 12h, created_at + 7d)`로 늘린다.

## 8. API (v1)

기본 주소는 클라이언트 상수 하나(`ONLINE_API`)로 둔다. 빈 값이면 온라인 기능 전체를 끈다. 플레이어 ID는 `X-Lumen-Player` 헤더로 보낸다.

| 요청 | 설명 | 성공 | 주요 실패 |
|---|---|---|---|
| `GET /v1/caches?layout=1` | 활성 보급품 목록. 플레이어 ID를 받지 않고, Worker 메모리에 30초 둔다 | `200 { enabled, now, caches: [{ id, slot, kind, note, charges, thanks, expiresAt }] }` | `503` 꺼짐·장애 |
| `POST /v1/caches` `{ layout, slot, kind, note }` | 보급품 두기 | `201 { cache }` | `400` 형식 오류, `409 slot_taken`, `429 limit` (사유: 플레이어 3개 / 하루 등록 / 전체 400 / 레이트) |
| `POST /v1/caches/{id}/use` | 보급품 쓰기 | `200 { kind, charges }` | `410 gone`(만료·소진), `403 own_cache`, `409 used_today`, `429` |
| `POST /v1/caches/{id}/thanks` | 고마워요 | `200 { thanks, expiresAt }` | `403 not_used`, `409 already_thanked`, `410`, `429` |
| `GET /v1/me` | 타이틀 화면 소식. `seen`에 오늘 1회 기록 | `200 { active, placed, uses, thanks }` | `503` |
| `DELETE /v1/me` | 내 온라인 기록 지우기 | `204` | `503` |
| `POST /v1/story` `{ events: [{ kind, id, skipped }] }` | 이야기 진행 집계(18.1절). 플레이어 ID를 받지 않는다 | `200 { accepted }` | `400 bad_events`·`bad_event`, `413`, `429 rate`, `503` |

- 2026-11-08부터 `GET /v1/caches` 응답에 `rules`(클라이언트 안내 문구용 규칙 수치)와 `runToken`(2단계 판 토큰)이 더해졌다(18.3·18.4절). 옛 클라이언트는 모르는 필드를 무시한다.

- 응답에는 `owner`나 다른 사람의 해시를 절대 넣지 않는다. 내가 둔 보급품인지는 클라이언트가 자기가 받은 `id`를 `localStorage`에 기억해 판단한다.
- CORS는 운영에서 `https://jeiel85.github.io`만 허용한다. localhost는 로컬 서버(`.dev.vars`)에서만 허용해, 로컬 게임이 운영 기록을 남기지 않게 한다. 다만 `Origin`은 브라우저 밖에서 얼마든지 위조할 수 있으므로 **남용 방지 수단이 아니다.**
- 클라이언트는 모르는 `kind`와 필드를 무시한다. 옛 클라이언트가 새 서버를 만나도 깨지지 않게 하기 위해서다.

## 9. 익명 식별

- **플레이어 ID**: 처음 온라인 기능을 쓸 때 `crypto.randomUUID()`로 만들어 `localStorage`의 `lumen.pid`에 둔다. 사람과 연결되는 정보가 아니며 화면에 보여 주지 않는다. 서버에는 `sha256(pid)`만 저장한다.
- **원문 IP는 저장하지 않는다.** 레이트 리밋 키로 `HMAC-SHA256(IP, 그날의 비밀값)`을 쓰고, 이 카운터는 48시간 안에 사라진다. 비밀값은 UTC 날짜마다 바뀌어서 날짜가 다르면 같은 IP의 해시끼리 연결되지 않는다.
- **한계를 숨기지 않는다**: 호스팅 플랫폼 자체의 접근 로그에는 IP가 남을 수 있고, 보존 기간은 플랫폼 정책을 따른다. 개인정보 안내문에 이를 적는다(12절).
- `localStorage`를 못 쓰는 환경(`src/storage.js`가 경고하는 경우)에서는 ID를 메모리에만 둔다. 판마다 새 플레이어로 취급되고 타이틀 소식은 비어 있다. 기능이 깨지지는 않는다.
- ID를 지우면(브라우저 데이터 삭제) 새 플레이어가 된다. 익명 설계라 이를 막을 수 없고, 막지 않는다. 그래서 남용 방지는 "사람 1명 = ID 1개"를 가정하지 않는다(10절).

## 10. 남용 방지

익명이라 한 사람이 ID를 여러 개 만드는 것을 막을 수 없다. 목표는 **피해의 상한을 정하고, 넘으면 빨리 끌 수 있게 하는 것**이다.

| 위협 | 방법 | 대응 |
|---|---|---|
| 대량 등록(스팸) | 스크립트로 ID를 바꿔 가며 `POST /v1/caches` | 플레이어당 활성 3개, IP 해시당 하루 6개, 전체 활성 400개 상한. 상한에 걸리면 `429`를 내고 기존 보급품은 지키며 새 등록을 거절 |
| 사용 횟수 고갈 | 새 ID로 남의 상자를 계속 사용 | IP 해시당 사용 하루 40회, 분당 쓰기 10회. 피해 상한은 "그날 몇몇 상자가 일찍 바닥남" |
| 고마워요 조작 | 자기 상자에 다른 ID로 고마워요 | 사용 기록이 있어야 가능(그만큼 횟수 소모), 상자 수명 최대 7일 상한 |
| 위치 조작 | 범위 밖·막힌 슬롯 | 슬롯 범위와 금지 목록 검사, 한 슬롯 하나 |
| 형식 조작 | 없는 `kind`, 큰 `note`, 거대한 본문 | 스키마 검증(열거형·정수 범위), 본문 1KB 제한 |
| 목록 대량 조회(비용·한도 소진) | `GET`을 반복 호출 | Worker 메모리 30초, IP 해시당 분당 30회(선택, 17절) |
| 무료 한도 소진으로 인한 정지 | 요청 폭주로 하루 한도 초과 | 클라이언트는 장애와 똑같이 처리(13절). 반복되면 2단계 대응 적용 |

2단계 대응(남용이 실제로 보이면 적용). 서버 쪽은 2026-11-08에 만들어 두었고 기본은 꺼져 있다(18.3절). 켜는 순서는 [server/README.md](../server/README.md) '2단계 남용 대응 켜기'.
- **판 토큰**: `GET /v1/caches`가 서명된 발급 시각을 주고, 두기는 발급 3분(게임 속 하루) 뒤부터만 받는다. 자동화 속도를 늦추는 정도의 장치다.
- **사람 확인(Cloudflare Turnstile 등)**: 두기 직전에만 요구한다. 마찰과 제3자 스크립트가 추가되므로 1단계에서는 넣지 않는다.

운영 장치
- **킬 스위치**: `settings.enabled = 'false'`로 바꾸면 `GET`은 `{ enabled: false }`, 쓰기는 `503`을 돌려주고 클라이언트는 온라인 요소를 숨긴다.
- **일괄 정리**: 기간·슬롯·소유자 해시 단위로 `removed_by='admin'` 처리하는 관리용 SQL을 서버 저장소에 둔다.
- **관찰**: 하루 등록·사용·`429` 수를 본다. 평소의 10배를 넘으면 원인을 확인한다(D-001의 운영 부담 참고).

## 11. 모더레이션

- **자유 텍스트를 받지 않는다.** 문구는 미리 정한 목록에서 고른다. 욕설·개인정보·링크 스팸을 걸러 낼 필요가 아예 생기지 않는다.
- 제안 문구(번호는 서버에 저장되는 값이라 순서를 바꾸지 않고, 추가만 한다):

  | 번호 | 문구 |
  |---|---|
  | 0 | (문구 없음) |
  | 1 | 같이 버텨요 |
  | 2 | 여기서 잠깐 쉬어 가요 |
  | 3 | 밤이 길어요, 조심해요 |
  | 4 | 곧 불이 켜질 거예요 |
  | 5 | 먼저 지나간 사람이 |
  | 6 | 아껴 쓰세요 |
  | 7 | 트럭에 기름 넣고 가요 |

  아이템 위치를 알려 주는 문구는 넣지 않는다. 수색 지점 내용물이 판마다 바뀌어 거짓말이 되기 때문이다(1절).
- 닉네임이 없으므로 신고 기능은 1단계에서 넣지 않는다. 남은 문제는 "보급품이 너무 많다·이상한 곳에 몰렸다" 정도여서 관리자 일괄 정리로 다룬다.

## 12. 데이터 보존·삭제·안내

| 데이터 | 보존 | 그 뒤 |
|---|---|---|
| `uses`, `thanks` | 기록 시각부터 90일 | 일별 집계 수치만 남기고 삭제 |
| `caches` | 만료·삭제 시각부터 90일 (자식 기록과 같은 기간) | 행 삭제 |
| `seen` | 90일 | 삭제 |
| 레이트 리밋 카운터 | 48시간 이하 | 자동 소멸 |
| 이야기 진행 집계 `story_daily`(2026-11-08 추가)·앱 몫 `story_app_daily`(2026-11-09 추가) | 400일 | 행 삭제. 사람을 가리키는 값(ID 해시·IP 해시)이 처음부터 없는 날짜별 횟수라 다른 기록보다 길게 둔다 |
| 정리 작업 실행 기록 `cron_runs` (2026-11-08 추가) | 최근 30번 | 그 앞은 삭제. 시각·성공 여부·지운 행 수·오류 메시지만 있다 |
| 플랫폼 백업 | 플랫폼 정책 (예: D1 Time Travel 무료 7일) | 삭제한 데이터도 이 기간 동안은 백업에 남는다 |

- 정리 작업은 하루 한 번 예약 실행한다(Workers Cron Trigger). 순서는 ① 전날까지의 일별 집계 → ② 90일 지난 `uses`·`thanks` 삭제 → ③ 만료·삭제된 지 90일 지난 `caches` 삭제다. 사용과 고마워요는 보급품이 살아 있을 때만 생기므로, 어떤 보급품의 자식 기록은 모두 그 보급품의 만료·삭제 시각보다 앞선다. 그래서 ②가 끝나면 ③에서 지울 보급품에는 자식 기록이 남아 있지 않다.
- **본인 삭제**: 설정의 "내 온라인 기록 지우기"가 `DELETE /v1/me`를 부른다. 서버는 ① 내 `uses`·`thanks`·`seen` 행을 지우고, ② 내 보급품을 `removed_by='owner'`로 내리고 `owner`를 `'deleted'`로 바꿔 나와의 연결을 끊는다. 다른 사람이 내 보급품을 쓴 기록은 그 사람의 기록이라 지우지 않고, 부모 행은 위 정리 작업이 90일 뒤에 지운다. 그 뒤 클라이언트가 `lumen.pid`를 새로 만든다. 남이 이미 받은 아이템은 그 사람의 판에 남는다.
- **안내**: 타이틀 화면에 한 줄 — "온라인 보급품: 무작위 ID와 보급품 위치를 서버에 저장합니다. 끌 수 있어요." — 과 README의 '개인정보' 절을 둔다. 저장하는 것, 저장하지 않는 것(원문 IP, 이름, 텍스트), 보존 기간, 삭제 방법을 적는다. 법적 판단은 이 문서의 범위가 아니다. 무작위 ID와 IP 해시라도 국내 개인정보 관련 의무에 해당하는지 출시 전에 따로 확인할 항목으로 남긴다. 확인할 것과 근거 조문은 [server/README.md](../server/README.md) '개인정보 법적 의무 확인'(법률 자문 아님)에 정리했다.
- **이야기 진행 집계(2026-11-08)**: 온라인을 켜 둔 플레이어의 게임은 장면을 끝까지 봤는지·건너뛰었는지, 장에 들어가고 마쳤는지를 보낸다(18.1절). 서버는 누가 보냈는지 남기지 않는다. 플레이어 ID 헤더를 받지 않고, IP는 분당 한도 확인(Cloudflare 레이트 리밋 카운터, 해시 키)에만 쓰고 D1에는 쓰지 않는다. 남는 것은 'UTC 날짜·장면 id·횟수·건너뛴 횟수'뿐이다. 그래서 "내 온라인 기록 지우기"로 지울 내 행이 따로 없다. README '개인정보' 절에 이 한 문단을 더한다.

## 13. 서버 장애와 오프라인 동작

원칙: `src/storage.js`가 저장소 실패를 다루는 방식과 같다. **온라인 요소는 부가 기능이고, 실패해도 게임은 계속된다.** 실패를 숨기지는 않는다.

| 상황 | 동작 |
|---|---|
| 판 시작 시 목록 요청이 3초 안에 안 오거나 실패 | 보급품 없이 시작하고, 한 번만 안내: "다른 생존자의 흔적을 불러오지 못했다." 목록이 늦게 도착하면 버린다(판 도중에 마을이 바뀌지 않게) |
| 두기 실패 | 아이템을 빼지 않는다. 사유별 안내(자리 있음·한도·연결 끊김) |
| 쓰기 실패 | 아이템을 주지 않는다. "연결이 끊겨 보급품을 열지 못했다." `410`이면 상자를 그 판에서 지운다 |
| 고마워요 실패 | 조용히 한 번 재시도하고, 그래도 실패하면 안내 |
| `enabled: false` | 온라인 요소와 '두기' 버튼을 숨긴다. 안내는 띄우지 않는다 |
| 무료 한도 초과(예: Workers 하루 요청 한도) | 장애와 똑같이 처리 |

- 오프라인 대기열(나중에 보내기)은 두지 않는다. 판이 짧고 상태가 판마다 초기화되어, 대기열이 주는 이득보다 엇갈림 처리 비용이 크다.
- 요청은 모두 `AbortController`로 시간 제한(목록 3초, 그 밖의 요청 5초)을 둔다. 게임 루프는 응답을 기다리지 않는다. 길게 누르기가 끝나면 요청을 보내고, 기다리는 동안 프롬프트에 "여는 중…"을 띄웠다가 응답이 오면 결과를 적용한다.

## 14. 성공 측정

### 14.1 지표 (서버 기록으로 계산)

| 지표 | 정의 | 의미 |
|---|---|---|
| 접속 플레이어 | 기간 내 `seen`의 서로 다른 `user_hash` | 분모. 지금은 이 숫자도 모른다 |
| 둔 플레이어 | 기간 내 보급품을 1개 이상 둔 서로 다른 `owner` | 남기고 싶은 마음이 있나 |
| **남의 것을 쓴 플레이어** | `uses.user_hash ≠ caches.owner`인 서로 다른 `user_hash` | 핵심. 흔적을 만나는 경험이 실제로 일어나나 |
| **쓰인 보급품 비율** | 남이 1번 이상 쓴 보급품 ÷ 둔 보급품 | 둔 것이 헛되지 않나(빈 마을 문제) |
| 고마워요 비율 | 고마워요 ÷ 사용 | 감정적 반응이 있나 |
| 다시 둔 플레이어 | 서로 다른 날에 2번 이상 둔 `owner` | 소식이 다시 오게 만드나 |

지표의 한계(2026-11-08, 이슈 #30). 판단할 때 이 방향의 오차를 감안한다.
- **접속 플레이어는 사람 수가 아니라 ID 수의 근사값이다.** 온라인을 켠 채 게임을 열고 타이틀 소식(`GET /v1/me`)까지 받은 ID만 센다. 그래서 (a) 온라인을 끈 사람과 소식 요청 전에 닫은 사람은 빠져 실제보다 적게, (b) 브라우저 저장소를 지우거나 "내 온라인 기록 지우기"로 ID가 바뀐 사람·여러 기기로 하는 사람은 둘 이상으로 세져 실제보다 많게 나온다. 익명 설계(9절)라 이 둘을 바로잡을 방법이 없다. 같은 한계가 '둔 플레이어'·'남의 것을 쓴 플레이어'에도 있다(한 사람이 ID 여럿이면 여럿으로 센다). 대시보드의 접속 플레이어 설명에도 적었다.
- **날짜는 UTC다.** `seen.day`와 일별 추이·이야기 집계의 날짜는 UTC라 한국 시간 오전 9시에 날짜가 바뀐다(한국 시간 = UTC+9). 그래서 한국 시간 자정~오전 9시의 활동은 **전날** 날짜로 보인다(예: 11월 8일 새벽 2시 KST = 11월 7일 17시 UTC). 이슈 #30에는 "밤 9시 이후 활동이 다음 날로 보인다"고 적혀 있지만 방향이 반대다. 접속 기록 `seen`은 기본 키가 UTC 날짜이고 시각이 없어, 한국 날짜로 바꾸려면 기록 형식부터 바꿔야 하고 이미 쌓인 기록은 다시 나눌 수 없다. 보급품·사용·고마워요는 시각(`created_at`·`used_at`·`at`)이 있어 바꿀 수 있지만, 그것만 바꾸면 같은 표 안에서 접속만 다른 날짜 기준이 된다. 그래서 바꾸지 않고 화면에 'UTC 날짜'라고 적어 둔다. 14일 판단처럼 시각으로 자르는 지표는 영향을 받지 않는다.

### 14.2 판단 기준 (제안, 출시 후 14일)

- **계속(랜턴 등 2단계로)**: 남의 것을 쓴 플레이어 ≥ 20명, 그리고 쓰인 보급품 비율 ≥ 40%
- **재검토**: 둔 플레이어는 있는데 쓰인 비율이 20% 미만 → 플레이어가 너무 적거나(빈 마을) 보급품이 눈에 안 띄는 것. 수명·노출을 조정해 1회 더 측정
- **중단**: 14일 동안 둔 플레이어 < 5명 → 킬 스위치로 끄고, 30일 뒤 데이터를 지우고, 클라이언트 코드를 걷어 낼지 정한다

숫자는 현재 이용자 수를 모르는 상태에서 잡은 출발값이다. 첫 주의 접속 플레이어 수를 보고 비율 기준으로 다시 맞춘다. 맞출 때는 14.1절 끝의 한계(접속 플레이어는 ID 수의 근사값)를 함께 본다. 접속 플레이어를 분모로 쓰는 비율은 ID가 바뀐 사람만큼 낮게 나온다.

### 14.3 빈 마을(콜드 스타트) 위험

비동기 온라인은 플레이어가 적으면 아무도 서로를 만나지 못한다. Threads 반응이 아직 적다는 점을 고려하면 **가장 큰 위험**이다.
- 수명을 길게(72시간~7일) 둔 이유가 이것이다.
- 실제 기록에서만 나온 문구를 보여 줄 수 있다. 예: "최근 7일 동안 생존자 12명이 이 마을에 보급품을 남겼다."
- **가짜 보급품이나 가짜 플레이어 흔적은 넣지 않는다.** 개발자가 직접 두는 보급품도 일반 플레이어와 같은 규칙을 따른다.

### 18.1 이야기 진행 집계 `POST /v1/story`

목적: 플레이어가 어느 장면까지 가고 어디서 건너뛰는지, 2~4장에 들어가고 마치는지를 **사람을 구별하지 않고** 센다. 이야기를 더 늘릴지 정할 근거다.

요청 (온라인 기능을 켠 플레이어만 보낸다. 끈 사람은 아무것도 보내지 않는다)

```json
POST /v1/story
Content-Type: application/json   (또는 text/plain — navigator.sendBeacon 용)

{ "events": [
  { "kind": "scene",   "id": "arrival", "skipped": false },
  { "kind": "scene",   "id": "dusk",    "skipped": true },
  { "kind": "chapter", "id": "2" },
  { "kind": "clear",   "id": "2" }
] }
```

| 필드 | 값 | 뜻 |
|---|---|---|
| `kind` | `scene` | 장면이 끝났다(끝까지 봤거나 건너뜀). 장면 하나를 한 번 볼 때 한 번 보낸다 |
| | `chapter` | 장에 들어갔다. `id`는 장 번호 문자열(`"1"`~`"4"`) |
| | `clear` | 장을 마쳤다. `id`는 장 번호 문자열 |
| `id` | `^[a-z0-9]{1,24}$` | 장면 id(`src/script.js`의 `SCENES[].id`) 또는 장 번호. 서버는 형식만 보고 목록은 모른다(장면을 더해도 서버를 다시 배포할 필요가 없다) |
| `skipped` | `true`/`false`, 생략하면 `false` | 건너뛰었는가. `scene`에만 `true`를 쓸 수 있다 |

- 요청 하나에 사건 1~20개, 본문 2KB 이하. 하나라도 형식이 틀리면 전체를 `400 bad_event`(배열이 아니거나 비었거나 20개 초과면 `bad_events`)로 거절하고 아무것도 세지 않는다.
- 응답: `200 { "accepted": n }`. 그날(UTC) 전체 상한(1만 건)에 닿으면 `accepted: 0`이고 그날은 더 세지 않는다. 클라이언트는 응답을 기다리지 않고, 실패해도 다시 보내지 않는다(관측용이라 잃어도 된다).
- 그 밖: `429 rate`(게임 쓰기와 같은 분당 한도 RL_WRITE), `503 disabled`(킬 스위치), `413`(본문 초과). 플레이어 ID 헤더(`X-Lumen-Player`)는 보내지 않는다.
- **클라이언트 묶어 보내기(권장)**: 사건을 메모리 대기열에 모았다가 ① 장을 마칠 때, ② 처음 화면으로 돌아갈 때, ③ 대기열이 10개가 될 때, ④ 탭이 가려질 때(`visibilitychange` hidden·`pagehide`) 한 번에 보낸다. ④에서는 `navigator.sendBeacon(url, new Blob([JSON.stringify(body)], { type: 'text/plain' }))`로 보내면 CORS 사전 요청 없이 닫히는 탭에서도 나간다. 동시에 보내는 요청은 하나만 둔다. 한 판에 장면이 30개 안팎이라 플레이어 한 명이 하루에 쓰는 요청은 몇 건이다.
- 저장: `story_daily(day, kind, id, n, skipped)` — UTC 날짜별 횟수와 건너뛴 횟수. 같은 요청 안의 같은 (kind, id)는 한 행으로 합쳐 더한다(D1 쓰기는 요청당 '서로 다른 id 수 + 1'행). `kind = 'total'` 행이 그날 받은 사건 수이고, 상한 확인과 더하기는 한 트랜잭션이라 동시에 와도 상한을 넘겨 세지 않는다.
- 웹·앱 나누기(2026-11-09, #53): `Origin` 헤더가 안드로이드 앱 출처(`https://localhost`, `src/rules.js` `storyAppOrigin`)와 같으면 같은 행을 `story_app_daily`(같은 열, `total` 행 없음)에도 더한다. `story_daily`는 출처와 상관없이 전체를 그대로 세고, 웹판 = 전체 − 앱이다. 하루 상한은 `story_daily`의 `total` 행 하나가 둘 다 맡아 두 표가 어긋나지 않는다. 클라이언트는 아무것도 더 보내지 않는다(이미 나간 앱 빌드도 나뉜다). 헤더가 없거나 다르면 웹으로 친다. 비공개 테스트 동안 테스터(앱)의 1장 완주·그만두는 장면을 웹판 데모 플레이어와 섞지 않고 보기 위해서다. 앱 요청의 D1 쓰기는 '서로 다른 id 수'만큼 늘어난다.
- 비용 상한: 하루 1만 건이면 D1 쓰기는 많아야 2만 행 남짓(그날 처음 보는 id의 행은 기본 키 색인까지 2행)으로 무료 한도(하루 10만 행)의 20% 안이다. 상한이 찬 뒤의 요청은 D1에 한 행도 쓰지 않는다(읽기 몇 행). 남용으로 상한이 차면 그날 이야기 집계만 멈추고 게임 쓰기는 남는다. 대시보드가 '오늘 받은 사건 / 상한'을 보여 준다.
- 개인정보: 누가 보냈는지 남기지 않는다(12절). 같은 사람이 같은 장면을 다시 보면 다시 세지므로 '도달한 사람 수'가 아니라 '본 횟수'다. id 형식만 검사하므로 누구나 엉뚱한 id를 셀 수 있다. 그 피해는 하루 상한 안의 잡음이다.
- 한계: 날짜는 UTC(14.1절). 탭이 장면 도중에 닫히면 그 장면은 세지 않는다(④로 줄인다).

### 18.3 2단계 남용 대응 (서버 준비, 기본 꺼짐)

10절의 두 장치를 서버에 만들어 두었다. `wrangler.toml`의 변수로 켜고, 기본은 둘 다 꺼짐(`"false"`)이다. **클라이언트가 아래 값을 보내도록 바뀐 뒤에** 켠다. 먼저 켜면 모든 두기가 거절된다.

| 장치 | 켜는 변수 | 클라이언트가 할 일 | 거절 |
|---|---|---|---|
| 판 토큰 | `RUN_TOKEN_REQUIRED = "true"` | 판을 시작할 때 받은 `GET /v1/caches` 응답의 `runToken`(문자열)을 기억했다가 `POST /v1/caches` 본문에 `"runToken"`으로 넣는다 | `403 run_token`(없음·위조·24시간 지남), `403 too_early`(받은 지 3분 전) |
| 사람 확인 | `HUMAN_CHECK_REQUIRED = "true"` + 비밀값 `TURNSTILE_SECRET` | 두기 직전에 Cloudflare Turnstile 위젯을 띄워 받은 토큰을 `POST /v1/caches` 본문에 `"humanToken"`으로 넣는다 | `403 human_check`(없음·실패), `503 human_check_unavailable`(확인 서버 장애), `503 misconfigured`(비밀값 없음) |

- 판 토큰은 강제하지 않을 때도 목록 응답마다 준다. 켜는 순간 이미 판을 시작한 클라이언트도 토큰을 갖고 있게 하기 위해서다. 토큰은 발급 시각과 그 HMAC(비밀값 `IP_HASH_SECRET`, 접두사로 IP 키와 분리)이고, 사람·기기와 묶이지 않는다.
- 사람 확인은 Turnstile 서버 확인(siteverify)에 원문 IP를 보내지 않는다. Turnstile 무료 플랜은 위젯 20개까지, 확인 요청 무제한이다([Turnstile Plans](https://developers.cloudflare.com/turnstile/plans/), 2026-11-08 확인). 대신 게임 페이지에 제3자 스크립트(challenges.cloudflare.com)와 사람 확인 마찰이 생기고, 처음 화면 개인정보 안내도 바꿔야 한다.
- 거절은 D1을 건드리기 전에 한다. 거절된 요청은 하루 한도 카운터를 쓰지 않는다.

### 18.4 클라이언트 안내 수치 `rules`

`GET /v1/caches` 응답에 `rules`가 붙는다. 클라이언트가 손으로 따라 적던 값(`src/main.js`의 `CHARGES`, `src/online.js`의 `MAX_MINE`·`REUSE_MS`·`KEEP_MS`)을 이것으로 바꿀 수 있다.

```json
"rules": { "charges": 8, "maxActivePerPlayer": 3, "reuseCooldownMs": 86400000, "maxLifetimeMs": 604800000 }
```

- 값은 서버 `src/rules.js`에서 온다. 필드 이름은 공개 API라 바꾸지 않고 더할 때는 끝에 더한다.
- 목록을 못 받은 판(장애·시간 초과)에는 `rules`도 없으니, 클라이언트는 지금 상수를 기본값으로 남겨 두고 받으면 덮어쓴다.
